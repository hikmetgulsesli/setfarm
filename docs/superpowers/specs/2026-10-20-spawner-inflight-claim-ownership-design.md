Root cause: spawnAgentNow awaits claimStep while compiler preClaim work may exceed the orphan threshold. This work has no spawned agent process yet. Orphan maintenance checks activeProcesses and drainingProcesses, but ignores the genuine pending claim invocation and requeues its still-owned claim. Role-level claimingSpawns is not exact enough to identify the runtime claim.

Chosen design: privately track exact pending invocation ownership by unique runtime session ID, owner instance ID, full claim agent ID and runtime agent ID. Register synchronously before awaitclaimStep and retain until all postclaim publication/ownership transfer work settles. A function invocation try/finally removes its own exact record on resolve, reject and every early return. Join the candidate claim to its durable runtime by exact claim/run/step/claim-agent identity. Skip orphan recovery only when that exact durable tuple matches the current pending invocation. Never split underscore IDs, infer ownership from role alone, protect unrelated runs, or persist synthetic authority.

Alternatives rejected: extending the orphan timeout only postpones the same race; exempting design/stories or relaxing owner equality hides invalid bindings; using role-level claimingSpawns suppresses unrelated orphan recovery; forging/rebinding a sealed compiler attempt changes authority. No chosen behavior changes compiler artifacts, retries, budgets, publication format, admission or schema.

Behavior: while a compiler invocation is genuinely pending, maintenance does not drain/retry/release its exact claim. Other genuine orphan claims remain recoverable, including another run with the same workflow/role. After the invocation settles, its memory record is gone and ordinary orphan/active/draining/completion handling applies unchanged. No timers or grace-period increases.
